对象：`541d6be` 之后的一轮整改，依据 GPT 对 issue #3 的审查意见。
每一项先记录**当前实现现状**，再记录**改动**，最后记录**验证方式**。

> 状态列：`待改` / `已改` / `已确认不改`

| # | 项 | 当前实现现状 | 问题 | 改动 | 状态 |
|---|---|---|---|---|---|
| 1 | spec 行映射 | `build()` 每步对 device 上的 `spec_sequence_masks` 调 `nonzero`；后改为在 pinned CPU 掩码上算，再用 `.to(device)` 上传 | `.to(device)` 未传 `non_blocking=True`，torch-npu 的 copy 实现会**先同步流**；等于把同步换了个位置 | 分配一块持久 device 缓冲 + pinned CPU 缓冲，按原生做法 `copy_(..., non_blocking=True)` 异步上传 | 已改 |

## 本轮改动后必须自证的三件事

1. 热路径上**不再有任何数据形状依赖的设备同步**：无 `nonzero`、无布尔索引、无阻塞 H2D。
2. 数值语义不变：启动自检（SSM + conv）仍全绿。
3. 边界处的安全：越界行、null 行、padding 行仍被跳过而不是写坏。

## 审查记录（改动后自查）

1. **参数顺序**：`_prepare_commit_plan_kernel` 22 个位置参数（含新增 2 个）与签名逐一对应；
   `_commit_gdn_state_kernel` 22 个位置参数（含 `num_record_rows`）与签名逐一对应；
   `_apply_align_kernel` 7 位置 + 1 constexpr，与签名一致。
2. **热路径同步源**：不再有 device `nonzero`、不再有布尔索引、不再有阻塞 H2D。
   保留的两处均为**每进程一次**（首步的 `torch.equal` 与 `tolist` 日志）。
3. **`_accepted_buffer.fill_(1)` 保留**：值恒为 1，但只要不能证明下游没有原位写回，
   去掉它就可能让卷积窗口用到上一轮的值——收益（约 5 µs）不值得这个风险，故保留并记录。
4. **生命周期**：映射缓冲每步重写，消费方（plan kernel、apply kernel）与写入同流；
   图重放期间 Python 不运行，但 consume 发生在图外的 commit 路径，仍每步上传。
5. **边界**：`apply_align` 在 `align_valid`/`align_col` 缺失时直接返回；
   plan kernel 只在 `ALIGN_MODE` 下写这两个缓冲，none 模式不会误用。
6. **pending 负载**：由 `{"request_indices", "rows", "context"}` 组成，context 与 payload
   同源，group 之间不会串用。
